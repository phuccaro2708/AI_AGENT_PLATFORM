# SECURITY

Personal tool, one user, one machine (ADR-010). Agents run with the user's full rights; there is no OS sandbox and, since 2026-11-11, no self-written permission gate. What limits an agent is the CLI's own permission system, driven by the flags the adapters pass: `claude --tools Read,Grep,Glob` (read-only) or `--tools Read,Grep,Glob,Edit,Write --permission-mode acceptEdits` (workspace-write); `codex exec -s read-only|workspace-write`. A task with no permissions gets no flag from us (Claude then refuses writes when run non-interactively; Codex stays read-only). Not re-measured with the real CLIs after the gates were removed. Older probe notes: `docs/ASSUMPTIONS.md`.

## Implemented

- Logger redaction (`shared-utils`): sensitive keys (token, apiKey, secret, password, authorization, cookie, …) are masked, and credential-shaped strings (Bearer, `sk-`, `ghp_`, `AIza…`) are scrubbed from values and messages. Tested. This is best-effort pattern matching, not a guarantee.
- Tauri capability `default` (P4-7, 2026-11-05) grants only `core:event:allow-listen` and `core:event:allow-unlisten` — no shell, fs, http, dialog, window, app, path, menu, tray or webview commands. App commands (`invoke`) need no permission and are gated in Rust by `ALLOWED_METHODS`. CSP set in `tauri.conf.json`. No WebSocket. Checked in the real app over WebView2 CDP: `emit`, window title, app version and path commands are refused by the ACL; not checked: the full UI by hand, `tauri dev`.
- Supply chain: `minimumReleaseAge` 14 days, exact version pins, install scripts allowlisted (`better-sqlite3`, `esbuild` only).
- `.gitignore` excludes `.env*`, `*.db`.
- Native confirmation of sensitive decisions (R3, 2026-11-06): `approvals.resolve`, `recovery.resolve`, `tasks.resolveReconciliation`, `agents.setSettings` and `agents.probe` (it runs the chosen program) are not forwarded by the shell until the person presses Allow in a native dialog opened by the Rust shell (`CONFIRMED_METHODS` in `lib.rs`). The dialog text comes from the sidecar (`confirm.describe`, built from stored state, secrets masked, env values never shown) and the shell forwards the same parameters it described; a sidecar error, an empty description or Deny forwards nothing (fail closed). `confirm.describe` is not in `ALLOWED_METHODS`, so the webview cannot choose the text. Tested with injected dialog results (Rust unit tests, `sidecar-confirm.test.ts`); NOT checked in the real app (dialog not clicked). Text that picks the program (command, args, env names) is refused rather than shortened when too long; free text is shortened only with a visible "NOT shown" marker. Limits: the webview still picks the decision and note it asks to confirm, can open dialogs at will, and can call every non-sensitive allowed method.
- Agent secrets (Phase 7B): API keys for the CLI agents live in the Windows Credential Manager, written by the native side (`secret_set`/`secret_delete`/`secret_names`). The webview can write or delete a secret and list names; no command returns a value. Secret names must end in `KEY`/`TOKEN`/`SECRET`/`PASSWORD`, so this cannot set `PATH` or `NODE_OPTIONS`. Values reach the sidecar only as `AGENT_STUDIO_SECRET__<PROVIDER>__<NAME>` environment variables at spawn; the sidecar removes them from its own environment at start and passes each agent only its own provider's secrets. Changing a secret restarts the sidecar and is refused while tasks are queued or running. Tested: no secret in the database, logs or IPC responses (`sidecar-secrets.test.ts`); real store round-trip is an opt-in `cargo test -- --ignored`.
- Agent launch settings (Phase 7B): command must resolve to a real executable; extra arguments cannot carry permission, tool, sandbox or working-folder flags; environment settings are an allowlist (proxies, `LANG`, `LC_*`, `TZ`, certificate paths). Settings are saved only after a probe that saw real CLI capabilities.
- Redaction of loaded secret values (`secrets.ts`, `createSecretRedactor`): the sidecar knows the exact values it hands to agents, so it masks them (`[REDACTED]`) at the single point where agent output enters the system: each agent event is masked once as the orchestrator ingests it, so the stored messages, the pushed `task.message` events, the summaries and context items the workflow engine derives, task `reason`s, adapter error messages and the sidecar's own error logs/responses all derive from the masked copy. The sidecar's stderr log stream is also masked line by line as a last line of defence. Values of every provider are masked, in raw and JSON-escaped form. Tested with fake agents that print the secret in text, tool call/result, usage, errors and thrown exceptions: the value appears in no SQLite table (read generically through `sqlite_master`), no database file bytes, no log, no IPC response (`logs.query`, `logs.search`, `tasks.*`, `context.list`, `agents.*`) and no pushed event (`sidecar-redaction.test.ts`).
- Limits of that redaction: it matches the EXACT value only. A value that was transformed (base64, URL-encoding, hashed, truncated) or split across two chunks/events is NOT masked. Values shorter than 6 characters are never masked (it would shred ordinary words). The prompt a person types is stored as typed (a secret pasted into a prompt is not masked, and masking it would change what the agent is asked). Whatever a CLI writes to its own transcript/session files outside this application is out of scope. The diagnostics export (`packages/diagnostics`, IPC `diagnostics.export`, Settings button; P4-6) runs the same redactor and has a leak test, so it is covered to the same extent; whatever the redactor misses is missed there too. The logger's pattern-based scrubbing (`sk-`, `Bearer`, …) remains a best-effort extra.
- Other limits: a secret becomes part of the agent process environment, so the agent (and anything it runs) can read it and can send it anywhere it can reach. Not an OS sandbox.

## Process and recovery

### Job Objects (P4-4) — lifecycle and memory, NOT a sandbox

- Sidecar: runs inside a Windows Job Object with `KILL_ON_JOB_CLOSE` (ADR-004), so its process tree dies with the app. Optional per-process memory cap via `AGENT_STUDIO_SIDECAR_MEM_LIMIT_MB` (unset = no cap).
- Per task: `agent-job-wrap` (`src-tauri/src/bin/`) wraps one CLI in its own Job Object (argv array, no shell, `--mem-limit-mb`, `--timeout-secs`). Tested on Windows: killing the wrapper kills child and grandchild; timeout kills the tree (exit 124); missing program exits 125; `&`/`;` in arguments reach the program verbatim.
- Whole-tree RAM: an opt-in host-side watchdog (`treeMemoryLimitMb`, polling, kills the tree; tested on Windows, not a hard cap, OFF in the real process). Limits: `--mem-limit-mb` is per process; `--job-mem-limit-mb` (`JOB_OBJECT_LIMIT_JOB_MEMORY`) is a hard commit cap for the whole tree, measured to work (R4), but it makes the over-limit allocation FAIL rather than killing the process, counts commit not RSS, and is wired into the default `jobWrap` config since Q3 (2026-11-07) with a deliberately generous 8192 MB (`AGENT_STUDIO_JOB_MEM_LIMIT_MB=<MB>` overrides it, `0`/`off` removes the cap); how a real claude/codex reacts to a failed allocation was NOT run, and no commit figure of a real CLI tree has been measured. A job grants no file, network or registry restriction: the process keeps the user's full rights. The orchestrator can now start `claude`/`codex` through `agent-job-wrap` (opt-in `jobWrap` option, tested with the real binary and with fake CLIs; see ASSUMPTIONS, Phase 4), and it is now ON by default in the real process when the installed binary is found (otherwise a warning and no wrap), while the whole-tree RAM watchdog stays OFF by default because it only polls and is not a hard cap (opt in with `AGENT_STUDIO_CLI_TREE_MEM_MB=<MB>`; `AGENT_STUDIO_JOB_WRAP=0` turns the wrapper off). `tauri build --no-bundle` places the binary next to the app exe; a real installer was NOT built (BLOCKED: it needs NSIS/WiX downloaded). Checked with real claude 2.1.318 and codex 0.166.0 (ASSUMPTIONS d9): they run through the wrapper, and Ctrl+C, CTRL_BREAK, killing the wrapper and killing an outer wrapper standing in for the app all left no descendant alive (trees of 6 to 20 processes). The wrapper now returns the CLI's full 32-bit exit code (it used to cut it to 8 bits, so 256 looked like success). Not checked: killing the real Tauri app with a real CLI inside.

### AppContainer / Windows Sandbox (P4-5) — documentation only, nothing built

ADR-002 keeps an OS sandbox out of 1.0. No prototype was written and nothing was run on this machine, so every statement below is design analysis, not a result.

- Idea: run each CLI under a restricted token or an AppContainer profile with capabilities limited to the worktree. Windows Sandbox (a disposable VM) is the heavier alternative.
- Expected obstacles (unverified): CLIs such as claude and codex need their own config/credential folders, the network and `%TEMP%`; an AppContainer denies these by default and needs explicit ACL grants on each folder, which changes system state. Windows Sandbox needs the optional feature enabled, is not available on Home editions (this machine is Home), and cannot share a live worktree without a mapped folder.
- Probe facts that do exist (P4-1 d, see `docs/ASSUMPTIONS.md`): codex `workspace-write` blocks writes outside the working folder (but treats `%TEMP%` as writable); claude `acceptEdits` blocks writes outside the working folder, while `--allowedTools Write` does not. Claude enforces by tool/path rules inside the CLI, not by the OS.
- **Not achieved:** no OS-level containment of agent processes; agents can read files and use the network as the user. Git worktrees remain branch isolation only. A Low Integrity Level probe (docs/ASSUMPTIONS.md d5 and d7, PARTIAL) showed Low IL blocks writes outside labelled directories without admin rights, but not reads of user files nor network; login/model calls under Low IL could not be verified (copying credentials into the probe area was blocked), though CLI startup, local state writes and git/node children worked inside the low area, so nothing is implemented and ADR-002 is unchanged. UI should warn that agents run with the user's privileges.

### Recovery (P4-8, recovery steps only)

On restart, tasks that were `running`/`waiting_approval` become `needs_reconciliation`; the person chooses resume, retry or abandon (`recovery.inspect` / `recovery.resolve`). Retry or resume of a task whose side effects cannot be verified is refused by the sidecar. The Peer Review engine resumes from the database after a person resolves the interrupted task (implementer or reviewer; `sidecar-resume.test.ts`); a custom `maxRounds` is stored on the workflow row (`max_rounds`) so a resumed workflow keeps it, and an interruption in round 2 is tested (`sidecar-resume.test.ts`, "Peer Review restarted in round 2 or later"; fake adapters, not the real CLIs). Earlier text (2026-11-06) said `maxRounds` was not persisted and round 2 untested; both were fixed later. Not checked in the real Tauri app.

### Dependency audit

- `pnpm audit`: 0 high/critical, 2 moderate, both dev-only and ACCEPTED: nested `esbuild` via `drizzle-kit` (dev server issue, never run in the product) and `minimatch` via `eslint` (DoS; the patch 11.0.1 is not yet 14 days old on 2026-11-05 and eslint pins the older range). Upgrade when a patch is at least 14 days old and compatible.
- `cargo audit`: 0 vulnerabilities, 2 warnings ACCEPTED: `proc-macro-error` (unmaintained) and `glib 0.18` (unsound) enter only through Tauri's GTK3 stack on Linux; neither is in the Windows build graph (`cargo tree --target x86_64-pc-windows-msvc`). Revisit if a Linux build ships.
- GitHub Actions in `ci.yml` are pinned to full commit SHAs. Not yet verified on a real runner at the time of writing.

### Git config from the repo (T19, 2026-11-06) — mitigated for `git-worktrees` only

- Probed with git 2.55.0.windows.3: a repo's own `.git/config` made `git-worktrees` run hooks, `core.fsmonitor`, `diff.*.textconv`, `diff.external` and filter drivers. Every git call from the package now carries `-c core.hooksPath=NUL -c core.fsmonitor=false` (`/dev/null` off Windows); both `diff` calls add `--no-textconv --no-ext-diff`; repo-defined `filter.*` drivers are refused unless listed in `allowFilters` (`UntrustedGitConfigError`). Regression test: `packages/git-worktrees/src/hostile-config.test.ts`.
- **Not covered:** git commands the CLI agents run themselves inside a worktree, Linux/macOS (not run), `include.path` and `extensions.worktreeConfig`. A worktree is still not a sandbox.

## Not implemented yet (do not assume)

- Any approval per command or per file. The former Policy Engine, the Claude `--permission-prompt-tool` gate and the Codex `app-server` adapter were removed (ADR-010); the code is on branch `claude/loving-lovelace-32lh71`.
- Per-task Job Object wrapper: `agent-job-wrap` and a whole-tree RAM watchdog are wired into the claude/codex adapters; the wrapper is ON by default in the sidecar when its binary is found, the RAM watchdog is OFF (opt-in) (installer itself not built; checked with real claude/codex, see ASSUMPTIONS d9). OS sandbox / AppContainer: not implemented.
- Git worktrees are branch isolation, **not** a security sandbox. See ADR-002.
