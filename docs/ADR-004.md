# ADR-004 — Process-tree cleanup on Windows: two layers

- **Status:** Implemented in Sprint A (A1, A2, A5). Evidence below comes from GitHub-hosted runners only; **not yet verified on a physical Windows device** (belongs to Sprint E2).
- **Date:** 2026-11-02
- **Relates to:** ADR-001 (sidecar), ADR-002 (isolation level).

## Problem

Agent CLIs start their own child processes. Cancelling a task, or the app dying, must not leave orphans. Node has no Job Object API, and a Job Object cannot be used to cancel one task without killing everything inside it.

## Decision: two complementary mechanisms

| Layer                         | Where                               | Covers                                | Mechanism                                                                                                                                                                                     |
| ----------------------------- | ----------------------------------- | ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| App death / crash / hard kill | Rust shell (`src-tauri/src/job.rs`) | the sidecar **and every descendant**  | Windows Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`; the sidecar is assigned right after spawn, before the first request. Descendants inherit membership.                            |
| Per-task cancel / timeout     | Node (`packages/process-manager`)   | one agent process and its descendants | Windows: `taskkill /PID <pid> /T /F` (argument array, `shell:false`). POSIX: child is `detached` (own process group) and the group is signalled (SIGTERM, then SIGKILL after a grace period). |

Rejected alternatives: Job Object only (cannot cancel a single task); `taskkill` only (does nothing when the app crashes; the sidecar's stdin-closed handling does not reach grandchildren).

## Related decisions made in the same sprint

- **Windows `.cmd`/`.bat` shims are refused**, not wrapped in `cmd.exe /c` (CLAUDE.md principle 3 forbids a shell). `resolveExecutable` classifies them as `shim`; `runProcess` returns `spawn_error`. Recent Node versions also refuse them with `shell:false` (`EINVAL`); a Windows-only test records that behaviour on whatever Node runs it. Whether the Claude Code / Codex installs on the target machine are `.exe` or `.cmd` is **unknown** and is decided by probes B1/B2.
- **Sidecar stderr** goes to `sidecar.log` next to the database (append-only file, no reader thread, so a full pipe cannot stall the sidecar). The file may contain agent output and is **not rotated** yet (Phase 4).
- **Task state machine** (A3) is enforced in `Repo.setTaskState` with compare-and-set; `needs_reconciliation` is never left automatically.

## Limits (be honest about them)

- The Job Object protects against _app_ death. It is **not** a security sandbox (ADR-002): it does not restrict files, network or privileges, and children can still do anything the user can.
- The assignment is not atomic with process creation. The sidecar spawns no children at startup, so nothing can escape in the gap; this ordering must be kept if the sidecar ever starts work at launch.
- If the sidecar is already inside a job that forbids nesting, assignment fails and `Sidecar::spawn` returns an error (no silent degradation).
- `taskkill /T` walks the parent→child links at the time it runs; a grandchild whose parent already exited can be missed (Windows keeps no reverse link). The Job Object layer covers that for app death, not for per-task cancel.
- On non-Windows hosts the Rust job module is a no-op (dev convenience).
- No process memory/CPU limits are set yet (Phase 4).
